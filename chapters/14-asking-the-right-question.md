# Asking the Right Question

Everything so far has been about catching a problem already sitting in a forecast. The cheaper move is upstream: asking well enough the first time that most of them never arrive.

## A vague question gets a vague answer wearing confidence

"Can we afford to hire someone?" sounds like a question. It is really several unstated ones bundled together — afford for how long, assuming what growth, accounting for what else we've already committed to — and left unstated, each one gets filled in by whatever the agent finds convenient, not necessarily what you actually meant. It is, close to word for word, the question that opened this book — the one that got a fast, confident, eighteen-months-of-runway answer that turned out to be wrong.

Length is not what separates a good version from a bad one. What separates them is whether the request states, up front, the things the rest of this book has you discovering afterwards:

Vague:

> "Can we afford to hire a new engineer?"

Better:

> "Build a runway model with growth rate, hiring plan, and pricing as adjustable parameters. Include every hire and cost we've already committed to, not just current headcount. Run it against a base case, a worse case, and a better case for growth, using rates you can justify against our actual last six months, not the best two. Before showing me the forecast, run the same model against last year's actuals and confirm it reproduces what really happened."

Notice what the second version actually is. Every clause is a chapter from this book, stated as a requirement instead of hoped for: a real parameterised model, not a one-off spreadsheet (Chapter 5); every already-committed cost included, not just the current snapshot (Chapter 9); a defensible growth rate and a real range, not one optimistic number (Chapters 8 and 10); a known-answer test before the forecast is trusted (Chapter 7). None of it requires you to know accounting. It requires knowing which questions exist, which is what the last thirteen chapters were.

The two versions do not return different-quality answers to the same question. They return answers to different questions. Ledgerly's memo answered the first one: eighteen months, cash positive throughout, deck ready to go out. The second question, asked of the same books, returns a company that runs out of money in month ten — because it forces the signed €7,000 hire into the model and the growth rate down from the 9.59 percent implied by "triples" to the three percent the trailing year actually shows. Same company, same file, eight months apart, and the only difference is what was asked.

## What a complete request contains

Not every request needs every clause above — a rough gut-check for a small decision doesn't need scenario planning the way a fundraise forecast does. But for anything a real decision will lean on, the complete version specifies:

**What's being modelled, with real parameters.** Growth rate, hiring plan, pricing — as adjustable inputs, not baked into the formulas (Chapter 5).

**Every commitment already made.** Hires with signed offers, contracts already renewed or already lost, not just the current snapshot (Chapter 9).

**Standard definitions.** Margin, CAC, LTV, burn, computed the way the rest of the world computes them, not reinvented for this spreadsheet (Chapter 6).

**A range, not one number.** Its width is what tells you whether the forecast can settle the decision at all (Chapter 10).

**Proof it was tested before it was trusted.** A known case — last year's real numbers — that the model gets right, run before the year that actually matters (Chapter 7).

## When the honest answer is to bring in a real professional

Most of what reaches you does not need one. Some of it does: a fundraise, anything touching how the company is taxed, anything with legal exposure if it turns out to be wrong. For those, an hour of a real accountant's or lawyer's time is cheap relative to what a wrong version of that particular decision costs — not because this book's discipline stops applying, but because some decisions deserve a second, professionally trained set of eyes on the reasoning in addition to it, exactly the boundary Chapter 1 and Chapter 11 both drew.

## What to ask for

No short list this time — one request, the template from the start of this chapter with the specifics taken out:

> "Before you build this: tell me what you're modelling and which inputs are the parameters, what already-committed costs or contracts need to be included, and how you'll test the model before I rely on it. Then build it as a real spreadsheet with visible formulas, run it against a case where we already know the answer, and give me a range — a base case and a realistic worse case — not just one number."

Ask it before the model is built rather than after the forecast arrives. The rest of this book is for when you did not, or when the answer still fails to add up once you have it.
